# FEEDBACK

A running log of real problems, ambiguities and suggestions found while building the **chat service**. Entries are only things actually encountered. Nothing here claims an end-to-end test that was not run.

**Verification status (2026-11-04):** the chat service, including the GitHub App / Telegram linking / PR evidence work, was built and tested against local mocks of the engine contract and of GitHub (`services/chat/mock-engine`) (`services/chat/mock-engine`). The real engine, a live Telegram bot, a live GitHub webhook and Bitrefill have **not** been exercised from this service yet. So there are no observations about the Bitrefill API itself in this file; the chat service never calls it. The engine developer should append Bitrefill-specific findings.

| ID | Area | Type | What happened | Workaround in chat service | Suggestion |
|---|---|---|---|---|---|
| F-01 | Engine contract: rules | Ambiguity | Only `draft` is named as a rule status. The values after enable/pause/resume are not specified. | Treat `draft` → show *Enable*, `paused` → *Resume*, `archived`/`disabled`/`deleted` → no button, anything else → *Pause*. | Document the status enum. |
| F-02 | Engine contract: notifications/triggers | Ambiguity | Only `purchase_delivered` is named as a notification `type`; trigger `reason` only shows `queued` as an example. | Delivered receipts use our template (and only for that exact type); every other type renders the engine's `text`, HTML-escaped, with an icon guessed from the type name. A trigger `reason` containing "duplicate" shows the duplicate message; unknown reasons stay silent. | Publish the enums for `type` and `reason`. |
| F-03 | Engine contract: rules | Missing capability | No endpoint to edit or delete a draft rule. The bot's *Edit / restart* creates a new draft and leaves the old draft behind. | The old draft is simply never enabled; `/rules` still lists it. | Add `DELETE /v1/rules/:id` for drafts (or `PATCH`). |
| F-04 | Engine contract: triggers | Ambiguity | Repository matching case-sensitivity is unspecified. GitHub's `repository.full_name` preserves case, and users may type `Acme/App`. | The webhook forwards GitHub's value unchanged; the rule stores the repo as the owner typed it. | Engine should compare repositories case-insensitively. Needs confirmation before the live demo. |
| F-05 | Engine contract: rules | Ambiguity | Is `autoApproveUpToUsdCents: 0` valid? The bot lets the owner enter 0 to mean "always ask me". | Sent as-is. Only the mock accepts it so far. | Confirm the accepted range. |
| F-06 | Engine contract: notifications | Ambiguity | Delivery semantics are not stated (at-least-once? are un-acked items returned again? ordering?). | Assumed un-acked items are returned on every poll. The worker keeps an in-memory set of IDs already sent to Telegram so a failed ack never re-sends the message. A restart in that window can repeat one message. | State the semantics; consider an idempotency key. |
| F-07 | Engine contract: errors | Ambiguity | The error body format for non-2xx responses is not specified. | The client looks for a string in `error`, `message` or `reason` (or `error.message`) and shows a truncated, escaped version. | Specify `{ "error": { "code", "message" } }`. |
| F-08 | Engine contract: notifications | Design gap | A notification addressed to a chat the owner never authorized (group, unknown, non-private) cannot be reported as "undeliverable". | The chat service withholds redemption data, tells the owner a notification was withheld, then acks so the queue doesn't clog. | Add a `nack`/failed state so the engine can surface this. |
| F-09 | Product design | Gap | There is no way to learn the USD price of a package before a purchase. Gift-card denominations are in the product currency (e.g. ₹50), but all limits are in USD. | The bot explains this, never converts silently, and asks the owner to pick a USD cap. | Expose an estimated USD price per package in `GET /v1/products/:id`, so the bot can show "≈ $0.60" and sanity-check the cap. |
| F-10 | Product design | Possible duplication | Both the engine (via notifications) and the webhook handler (`"PR merged. Checking your spending policy."`) may tell the owner that a trigger arrived. | The webhook sends its message only for reason `queued` and for duplicates. | Decide which side owns the "trigger received" message once the real engine is wired up. |
| F-11 | Tooling | Minor | `npm install` (npm 11) printed an `install-scripts` warning for esbuild's postinstall. | None needed: `tsx` and `vitest` ran fine afterwards. | n/a |
| F-12 | Bounty spec | Resolved | The chat side was first built against an *assumed* bounty contract because the engine's real schemas were not in the repository. The two diverged in every shape (confirmed: the real engine answered the assumed `linkGithub` body with HTTP 400). | The chat client, evidence collector, pipeline, Telegram flow and mock were rewritten to the engine's canonical schemas (`services/engine/BOUNTY_API.md`). `tests/integration/ai-bounty-e2e.test.ts` drives the chat code against the **real** engine over HTTP, so a future drift fails a test instead of production. | Keep the E2E suite in CI. Mock-only suites are not compatibility evidence. |
| F-13 | Bounty contract | Resolved (one engine addition) | The engine had no way to revoke a verified GitHub identity. Enable/pause/resume already existed as `POST /v1/rules/:id/(enable\|pause\|resume)`; a repository needs no disconnect call because a paused rule cannot finalize. | Added `POST /v1/github/links/unlink` (soft revoke, migration `003_identity_revocation.sql`): revoked links are ignored by every authorization lookup, history keeps its references, only the same GitHub identity can re-link. Repository revocation pauses the rule via the existing owner-checked route. | Review migration 003. A revoked identity cannot be taken over by another Telegram user (409), by design. |
| F-14 | GitHub docs | Gap | GitHub's REST reference for "Get rules for a branch" (read on 2026-11-04) lists no fine-grained permission for the endpoint. Required status checks come from it, and classic branch protection needs Administration access we deliberately don't request. | Required checks are best effort: if unreadable, evidence has `requiredChecks: null` and an explicit `required_checks_unknown` issue. Not verified against a real installation. | Verify on the real app before relying on `requiredChecks`. |
| F-15 | GitHub App design | Constraint | GitHub does not allow a Setup URL when "Request user authorization (OAuth) during installation" is checked (registration docs). We want a verified identity after install. | Leave that box unchecked, use the Setup URL, and send the user through our own OAuth round trip after install; `installation_id` from the redirect is ignored. | n/a |
| F-16 | Tooling (my test mock) | Own bug, fixed | The first run of the mock GitHub server rejected Octokit's JWT calls: Octokit sends `bearer <jwt>` (lowercase scheme) and the mock only accepted `Bearer`. | Mock is now case-insensitive. Real GitHub accepts both. | n/a |
| F-17 | Telegram | Limitation | Telegram URL buttons can't point at `localhost` or plain IPs, so `/connectgithub` and `/linkgithub` need a public HTTPS tunnel even for local testing. | Documented in `docs/TELEGRAM_SETUP.md`. | n/a |
| F-18 | Identity linking | Residual risk | A Telegram user can forward their link to someone else, who signs in with their own GitHub account. The binding goes through a browser confirmation page that names both accounts, and the engine rejects (409) a GitHub ID already linked elsewhere, but a deceived person could still confirm. | Browser binding cookie, single-use state and an explicit confirm page; `/unlinkgithub`. | Consider a Telegram-side confirmation tap by the contributor. |

| F-19 | Engine/chat integration | Defect found | The engine caps review attempts per policy+PR (`LLM_REVIEW_MAX_CALLS_PER_PR`, was 3). Opened + labeled + one push + the mandatory merged re-review would already hit it, and the *final* review is the one that matters. | Default raised to 6 (max 10). The chat fingerprints evidence (without its timestamp) and reuses a recent identical review instead of re-submitting, and reports `REVIEW_CALL_LIMIT` to the owner. | Tune per repository activity. |
| F-20 | Chat client | Defect fixed | `EngineClient` mapped every HTTP 403 to "unauthorized token", hiding real engine business refusals (e.g. `REPOSITORY_NOT_AUTHORIZED`). | Only 401 means a bad token now; `EngineError.code` carries the engine's error code. | n/a |
| F-21 | Engine contract | Ambiguity | Label authorization must be bound to the PR head at label time; the REST API does not expose the head at label time. | The chat records the *signed* `labeled` webhook (actor, head SHA, time) and only the connected maintainer's numeric ID counts; the maintainer's `APPROVED` review on the exact head with resolved threads is the alternative. A push invalidates the label until re-applied. | Confirm this is the intended UX (maintainer re-labels after each push). |
| F-22 | GitHub API | Limitation | Review-thread resolution is only available through GraphQL; REST cannot say whether feedback was resolved. | GraphQL `reviewThreads` is read with the installation token; if unreadable, feedback counts as unresolved and the review-based authorization is withheld (flagged `review_threads_unavailable`). | Verify on a real installation. |
| F-23 | Required CI | Constraint | The engine only treats CI as complete if every *required* check was enumerated. We can only enumerate required checks from rulesets (no Administration permission), so a repo without a ruleset requiring a status check can never satisfy `requireSuccessfulCI`. | Documented in `docs/GITHUB_APP_SETUP.md`; the demo repository needs a ruleset. | Not verified on a real installation. |

## Integration audit (2026-11-04)

F-01/F-02/F-04/F-05/F-06/F-07 are now exercised against the actual engine HTTP interface in `tests/integration/baseline.test.ts`. The engine uses `draft`, `enabled`, `paused`, lowercase canonical repository identities, zero as the always-ask threshold, structured error bodies and an at-least-once outbox. F-10 is resolved by scope: the chat webhook owns the immediate eligible-trigger notice; the engine owns durable purchase outcomes.

Confirmed and fixed: transient Telegram `getChat` lookup failure discarded redemption by ACKing a redacted warning; exception messages could leak redemption into logs; numeric-only recipient validation could enable unlinked chats; the owner lacked a final receipt when the recipient differed; simulation bypassed quote/order rechecks and could not exercise private redemption relay. Regression and full HTTP E2E coverage are included. F-03 (draft cleanup), F-08 (explicit negative ACK) and F-09 (estimated price UX) remain outside baseline scope. ACK retry suppresses duplicate messages within one worker; a process crash after Telegram acceptance but before ACK can still repeat that private notification. No paid request is retried.

Safe external checks passed for Telegram identity/polling and temporary HTTPS routing. Actual Bitrefill reads are blocked by absent credentials. Genuine GitHub event delivery and a paid purchase remain manual/unverified. See `docs/BASELINE_VERIFICATION.md`.
